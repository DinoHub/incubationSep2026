# Adding auth to an MCP server

This takes a working MCP server and puts an identity boundary in front of it.
The mechanical half is scripted. The half that needs judgment — which role each
tool requires — is yours, and it is the half that decides whether any of this
means anything.

## The two boundaries, and why they fail differently

Authentication and authorization get discussed as one topic and are enforced at
two different moments, which is why their failures look nothing alike:

- **Authentication: who is calling?** Checked during the connection handshake,
  before any tool is reachable. A missing or invalid token gets a real
  **HTTP 401** and the connection is refused — no tool code runs.
- **Authorization: may this caller do *this*?** Only meaningful once a specific
  tool is being called inside an already-authenticated session. MCP has no
  per-tool HTTP status, so a denial comes back as a **tool result marked as an
  error**, naming the role that was missing.

Getting a 401 where you expected a tool error, or the reverse, almost always
means you are testing the wrong boundary. Both are checked separately, in
different tests, for this reason.

There is a third thing people expect to be a boundary and is not: **token
expiry**. An access token is short-lived on purpose — five minutes here — and
every request re-verifies it, so an open session starts failing the moment it
lapses. The answer is never a longer token; it is a refresh token, which the
host trades for a new access token on its own. That is why the realm ships a
public client for interactive sign-in, and why handing a user a static
`--header` is the wrong advice: a pasted token cannot renew itself.

## Workflow

### 1. Check the starting point

The script expects a project from the `mcp-server-scaffold` skill:
`http_server.py`, `test_server.py`, `Dockerfile`, and `docker-compose.yaml` with
an `mcp-server` service. It refuses rather than half-patching something else. If
there is no such project, scaffold one first.

Settle two things before running it:

- **Role names.** Defaults are `tools:read` and `tools:write`. Two roles split
  read from write, which is the split that matters most often; pass
  `--role-read` and `--role-write` for domain names that read better.
- **Which role each tool needs.** Sort the tools into "reads state" and "changes
  state". Anything that writes, deletes, spends money, or sends a message is a
  write, even when it returns something read-like.
- **The OAuth callback port.** Default 8123, registered in the realm as
  `http://localhost:8123/callback`. Change it with `--callback-port` only if
  something else on the machine already owns that port; whatever you pick has to
  be passed to `claude mcp add --callback-port` too.

### 2. Run the script

```bash
python <skill-dir>/scripts/add_auth.py --dir ./my-server --dry-run   # see the plan
python <skill-dir>/scripts/add_auth.py --dir ./my-server
```

It writes `auth.py`, `test_auth.py`, `keycloak/realm-export.json`,
`.env.example`, and a `healthcheck.py` that checks the metadata endpoint; adds
PyJWT to `requirements.txt`; adds the new files to the `Dockerfile`; and patches
`docker-compose.yaml` with the auth environment and the `keycloak` and
`test-auth` services. Everything it replaces is backed up to `*.pre-auth`.

It also drops two reference files, `test_server_identity_snippet.py` and
`README-auth-section.md`, for the edits below. Delete them once used.

### 3. Wire the server module

Add the import and the two constructor arguments:

```python
from auth import JWKSTokenVerifier, auth_settings, require_role

mcp = MCPServer(
    "...",
    instructions="...",                     # say which role each tool needs
    token_verifier=JWKSTokenVerifier(),
    auth=auth_settings(),
)
```

Then make `require_role(...)` the first line of every tool:

```python
@mcp.tool()
def read_file(name: str) -> FileInfo:
    """..."""
    require_role("tools:read")
    ...
```

Update the `instructions` string to say which role each tool needs. A model that
knows it lacks a role stops retrying a call that cannot succeed.

Do not reach for a server-wide `required_scopes` instead. It is deliberately
empty: any authenticated caller may open a connection, and privilege is decided
per tool. The MCP spec's own "Common Pitfalls" guidance says to verify scopes
per tool on the resource server rather than behind one catch-all scope.

### 4. Fix the in-process test, which auth just broke

`test_server.py` now has no identity, so every guarded tool fails with "the
caller is not authenticated" — a real regression the script cannot fix for you,
because it does not know your tools. Fold in
`test_server_identity_snippet.py`: it sets the auth context directly, so the
fast test can impersonate a reader and a writer.

This makes that test better than it was. One in-process run now checks both the
allow and the deny path for every tool, in about a second, with no Keycloak and
no network. Cover three cases: a reader succeeding on read tools and being
refused write tools, a writer succeeding on everything, and no identity at all
being refused.

**What it cannot check is authentication.** The in-process client never crosses
the HTTP layer where tokens are verified, so a completely broken verifier still
looks fine here. Anyone who runs only this test has tested authorization and
nothing else. Say so when you report.

### 5. Fill in the full-stack test

`test_auth.py` needs one row per tool in `EXPECTATIONS`: the tool name, the role
it requires, and arguments that would succeed if the caller held that role. The
matrix is derived from it — an identity with the role must succeed, one without
must be refused, and the denial must name the role. The write-ish rows really
run, so keep their arguments harmless.

### 6. Verify

```bash
docker compose --profile dev up -d --build
docker compose run --rm test              # roles, in-process, no Keycloak
docker compose run --rm test-auth         # tokens over HTTP, real Keycloak
```

Both, always. They cover different boundaries, and neither substitutes for the
other. Report which passed. If the stack cannot start, say so rather than
implying the boundary was verified.

`test_auth.py` also checks two things that are easy to get wrong and produce
identical-looking 401s: that the refresh token really buys a working access
token, and that the metadata document advertises an issuer URL reachable from
outside Docker. A host runs on the developer's machine, so an issuer spelled
`http://keycloak:8080` passes every other check here and still leaves nobody
able to sign in.

### 7. Tell the user what changed for callers

Any client that worked before now needs a token, so registration changes. Do
**not** hand them a static `--header`: an access token lasts five minutes, a
pasted one cannot renew itself, and the connection dies and stays dead. A host
that sees an `Authorization` header also stops there rather than signing in, so
the header actively disables the thing that would have kept it working.

Give them the sign-in flow instead. The realm ships a public client for it, and
the host stores a refresh token and renews on its own:

```bash
docker compose --profile dev up -d

claude mcp add --transport http --scope user \
  --client-id claude-code --callback-port 8123 \
  <slug> http://localhost:<port>/mcp
claude mcp login <slug>       # browser sign-in; dev-writer / dev-writer-password
claude mcp list               # confirms it connected
```

**Both flags are required, and leaving out `--client-id` is the failure people
hit.** Without it the host attempts Dynamic Client Registration, and Keycloak
answers `Policy 'Trusted Hosts' rejected request to client-registration
service` — a 403 at `claude mcp add` time that reads like the server is down.
Relaxing that policy is not the fix: Keycloak's `Full Scope Disabled` policy
strips realm roles from any client registered that way, so sign-in would work
and every tool call would then fail with an empty role list. Name the
pre-registered public client instead. `--callback-port` has to match a redirect
URI in the realm, which the script registers from its own `--callback-port`
(default 8123); any other port is refused with `Invalid parameter:
redirect_uri`.

The roles come from the login, not the host: `dev-reader` gets a read-only
connection, `dev-writer` gets both.

Say plainly that an unauthenticated client now gets a 401, that access tokens
last five minutes and are renewed from the refresh token without anyone pasting
anything, and that the whole session expires after the realm's idle timeout
(8 hours), at which point `claude mcp login` again is the fix.

For CI or anything headless, where no browser can complete a sign-in, point them
at the machine identities plus a `headersHelper` that mints a token per
connection. That is a re-mint, not a refresh, and it needs the client secret on
the box.

## What gets generated

| File | Role |
| --- | --- |
| `auth.py` | Token verifier, `auth_settings()`, and `require_role()`. Reads no config at import time. |
| `keycloak/realm-export.json` | Realm, two roles, two machine identities, and a public client plus two human logins for the interactive sign-in that yields refresh tokens. Imported on boot. |
| `test_auth.py` | Full-stack check: 401s, the metadata document, the refresh cycle, and the role matrix. |
| `healthcheck.py` | Replaced; now checks the metadata endpoint rather than the bare port. |
| `.env.example` | The knobs for pointing at a real provider. |
| `docker-compose.yaml` | Patched: auth environment, plus `keycloak` and `test-auth`. |

## Adding a tool later

Do not re-run the script; it refuses once `auth.py` exists. Add
`require_role(...)` to the new tool, add a row to `EXPECTATIONS`, add a case to
`test_server.py`, and rerun both tests.
